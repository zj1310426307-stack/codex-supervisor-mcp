# Phase 04 design

Phase 04 turns the v0.3 safety model into an evidence-oriented local-live
baseline without changing authority: ChatGPT or `supervisorctl` supervises,
Codex implements in one isolated worktree, the verifier independently checks a
snapshot, and a human alone owns commit, push, merge, release, and deployment.

## Runtime topology

The recommended topology is:

`ChatGPT -> Secure MCP Tunnel -> loopback Supervisor in WSL2 -> Codex App Server stdio -> task worktree`

The Supervisor and Codex run natively in the same WSL2 environment. Docker or
Podman is used only for the verifier. The root Dockerfile remains an
experimental MCP-server-only image; it has neither Codex nor a signed-in
identity and is not a complete Supervisor deployment.

## Compatibility gate

Every live Codex connection is bound to evidence generated by the selected
runtime itself:

1. read `codex --version`;
2. generate the version-specific App Server JSON Schema bundle into an isolated
   temporary directory;
3. hash the complete bundle canonically;
4. require all stable client and server methods;
5. validate the nested turn and approval shapes used by the Supervisor;
6. record whether the experimental API was explicitly requested;
7. bind the result to the exact App Server connection generation.

Unknown or incompatible evidence blocks control operations. Health, task
diagnostics, runtime-capability reporting, and the frozen read surface remain
available. Experimental methods are never substituted for a missing stable
method.

## Evidence tracks

- `npm run preflight:wsl2` is read-only and reports exact environmental
  blockers without repairs.
- `npm run smoke:codex` uses a real CLI only, awaits the initialize response
  before `initialized`, keeps stdin open through `account/read`, and requires
  proven exit plus stdout drain.
- `npm run e2e:codex` is explicitly acknowledged, operates only on a newly
  created no-remote disposable repository, and requires a real digest-pinned
  local verifier image.
- `npm run smoke:mcp` starts the real HTTP MCP stack twice and uses the official
  MCP client SDK to scan Restricted and Full-control mode.
- ChatGPT Web acceptance is a separate human-operated track. Local scans never
  turn its `NOT_RUN` state into PASS.

## Security invariants

- Restricted mode is the configuration default.
- Remote binding still requires bearer authentication plus exact Host and
  Origin allowlists.
- Obvious bearer placeholders are rejected.
- One shared redaction core protects MCP success/error results, events, the
  state ledger, Operator CLI output, verifier output, and live artifacts.
- Redaction occurs before truncation.
- Verification has no host fallback and accepts only
  `image@sha256:<64-hex>` identities from trusted local configuration.
- Container creation enforces no network, read-only root and worktree,
  non-root uid:gid, dropped capabilities, no-new-privileges, and explicit PID,
  memory, CPU, IPC, and tmpfs limits.
- Cleanup and reconciliation remain exact-identity operations; uncertain proof
  stays quarantined.

## Version and schema

The package/server/client identity is v0.4.0. The tool counts remain 13 and 23.
The tool Schema hash changes because Phase 04 makes the catalog JSON Schema
byte-equivalent to the real SDK `tools/list` representation for strict union
inputs by including the top-level object type. No tool is added and no authority
is broadened.
